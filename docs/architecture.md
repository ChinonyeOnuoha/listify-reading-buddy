# Architecture

## Stack
A client-side React 19 app using TanStack Start/Router (one route, `src/routes/index.tsx`), Vite, Tailwind CSS v4 and Radix UI primitives (dialogs, menus, popover), with lucide icons. Tests use Vitest and Testing Library. The project was generated on Lovable and is built for Cloudflare by default (`npm run build`); `NITRO_PRESET=node-server npm run build` makes a build that runs locally with `node .output/server/index.mjs`.

Main parts:
- `src/routes/index.tsx` — which corner and screen is showing, how the steps connect, and the confirmations and Undo messages.
- `src/components/app/` — the screens: setup steps (`setup.tsx`), bringing a passage or pages (`BringStep`), the story window (`Stories`), the reader (`Reader`), the recording controls (`Recorder`), listen back and the children’s reflection (`Review`), the sample (`Sample`), Saved (`Saved`), and shared dialogs, confirmations and messages (`ui.tsx`).
- `src/components/nook/Nook.tsx` — the illustrated reading nook.
- `src/components/reading/` — `useRecorder` (recording), `PageViewer` (zoom and pan for photographed pages), `Companion` (Buddy), `BookMark` (the logo book), `InstallButton`.
- `src/lib/reading-session.ts` — one corner’s session (text, pages, recording, story and page), restored from and kept on the device. `src/lib/device-store.ts` — the IndexedDB store behind it. `src/lib/nook-memory.ts` — the nook’s remembered choices. `src/lib/sound.ts` — the optional sound cues.
- `src/lib/pwa.ts` — install, offline and update state. `tools/` — the service-worker template and the build plugin that stamps it.
- `src/components/children/`, `src/content/stories/` — the children’s story reader and credits, and the corner’s eight built-in stories from African Storybook, Book Dash and StoryWeaver (see [children-corner.md](children-corner.md)); Book Dash asks for its logo with its books, so `public/credits/book-dash-logo.svg` is served from the app’s own origin. Story text is one small module per story, loaded only when that story opens; pictures live in `public/stories/` and load lazily page by page.
- `lab/` — the development-only AI feasibility lab (see [ai-feasibility.md](ai-feasibility.md)); it has its own Vite root and is not part of the app.

## How recording works (and why)
The first version used the browser's MediaRecorder, which writes compressed audio. That can't give a dependable pause-and-listen: a half-finished compressed file isn't guaranteed to play (Safari's MP4 may only be finalised when recording stops), and gluing separately recorded compressed files together doesn't make a valid file. So the recorder now captures raw audio samples with Web Audio (an AudioWorklet, with a ScriptProcessor fallback for older browsers), keeps them in memory at 16 kHz mono (~2 MB per minute), and builds a standard WAV file whenever something needs to play — for "Listen so far" and for the final recording. Pausing simply stops adding samples, so there's no artificial silence and nothing is duplicated. Nothing is uploaded and no paid service is involved.

## Install and offline (PWA)
Reading Buddy can be installed as an app on browsers that support it.
- **Install:** a compact "Install app" control at the foot of the home panel when the browser offers installation (Chrome, Edge, Android). On iPhone/iPad it opens a small popover with the steps: Safari → Share → Add to Home Screen. It's hidden once installed (standalone mode).
- **Manifest and icons:** `public/manifest.webmanifest` (standalone display, `#0E1830` theme and background), icons in `public/icons/`: ivory RB on ink blue with the apricot bookmark companion hanging above the B (192, 512, maskable 512, Apple 180 and a 32px favicon).
- **Offline:** `public/sw.js` caches the app shell (start page, built scripts and styles, fonts, icons). After one online visit the app opens and works offline, including recording and playback; if nothing is cached yet, `offline.html` explains. An in-app note appears while offline.
- **Updates are detected by build, not by a hand-edited number.** The service worker is a template (`tools/sw/sw.template.js`); every production build stamps it (`tools/sw-plugin.ts`) with an id derived from the hashed names of all built scripts and styles plus the contents of the files in `public/`, and with the exact list of files to precache. Same code → same worker; any change → a new worker, which browsers detect (the page also checks whenever you return to the tab, and registers with `updateViaCache: "none"`). The build fails loudly if the template's placeholders disappear.
- **Updates never interrupt anyone.** A new worker installs but waits (install never calls `skipWaiting`); the running version keeps serving its own caches. "A new version of Reading Buddy is ready — Update now" is offered **only on the home screen and never while a recording is in progress** (everything else is already kept on the device, so reloading loses nothing), and the update is applied only by pressing it (or once every copy of the app has been closed).
- **Cache housekeeping is limited to Reading Buddy's own caches** (`reading-buddy-<build>-shell`, `reading-buddy-<build>-assets`, `reading-buddy-fonts`, and the first release's `rb-v<n>-…` names). Other caches on the same origin are never read or deleted.
- **The service worker never stores passages, page photos or recordings**; those are kept in the app’s own IndexedDB store (below), which the worker never reads.
- The service worker only registers in production builds (not on the dev server). `vite preview` can't run this app's Cloudflare-targeted build; to test it locally build with `NITRO_PRESET=node-server npx vite build` and run `node .output/server/index.mjs`.

## Kept on this device
Reading Buddy has no accounts or database for user content, and uploads nothing, with one optional exception: AI feedback for adults (below).
- **Reading content** (pasted text, page photos as their original image files, the words added for a page, recordings as WAV or the uploaded audio file with any AI feedback notes made for them, and in the children’s corner the chosen story and the page reached) is kept in the browser’s **IndexedDB** for this site, one entry per corner (`main` and `children`). Writes are coalesced so typing doesn’t write on every key. It comes back on the next visit.
- **The nook’s choices** (minutes, cushion, beanbag, the corner’s reading time, Sound, and whether the one-time notes have been shown) are kept in `localStorage`. They contain no reading content.
- **Deleting:** Saved on this device lists each corner’s content with its size and deletes it (with Undo); Delete all removes both corners’ content; Forget my nook resets the remembered choices. Deleting a page, a recording or a session removes it from the store once the Undo time has passed. A recording’s AI notes are part of the recording’s entry, so they go wherever it goes: deleted with it, kept with it on Undo, and replaced when it is recorded again.
- **Storage:** the first save asks the browser to keep the site’s storage under pressure (`navigator.storage.persist()`); Saved shows the browser’s own estimate of free space. Where IndexedDB or `localStorage` is unavailable (some private windows, blocked site data), the app still works and the session lasts for the visit only.
- **Shared devices:** anyone using the same browser profile can open what is saved; Saved says so.

## Privacy and network behaviour
No content is sent anywhere, except a recording’s audio for optional AI feedback when an adult asks for notes (above).

What was checked, and how:
- **Source inspection:** the app code (`src/`, excluding tests) contains no `fetch`, `XMLHttpRequest`, `sendBeacon` or WebSocket calls for user content. The only `fetch` calls are the server entry's request handler and one that reads a recording's own `blob:` URL back into a file so it can be kept on the device (a local read; nothing leaves the browser).
- **Fonts are self-hosted:** Atkinson Hyperlegible Next, Andika and DM Serif Display are installed as npm packages, bundled into `/assets/` and precached by the service worker. The page makes no request to a font service or any other third party.
- **Service worker:** caches the app's own files, including the fonts. It never sees passages, photos or recordings. Story pictures are *not* cached, so they need a connection (the story text is part of the cached scripts).
- **Children’s corner:** the stories and covers are served from the app’s own origin; the corner adds no third-party request. Its source links (About this story) are ordinary links that open only when clicked.
- **Lovable's editor preview:** the app's error boundary forwards a runtime error's message, stack and route path to a reporting hook *if* one exists on the page (`src/lib/lovable-error-reporting.ts`). That hook is only present inside Lovable's editor preview; it is not part of this app, and what Lovable's tooling does with it was not inspected. No passage, photo or recording content is passed to it.
- **Not checked:** requests made by a hosting platform's own scripts or headers outside the app's code, and any browser extension behaviour.

The development lab is separate: it downloads speech and OCR model files from public CDNs and runs them locally in the browser. Cloud AI has been used twice, never by the app: one manual comparison done by hand outside the project ([ai-feasibility.md](ai-feasibility.md)), and an adult-only lab experiment (`lab/cloud/`, a local Node script run by hand) that sent six test recordings to Deepgram and AssemblyAI with keys from a git-ignored `.env.local` ([ai-feedback-experiment.md](ai-feedback-experiment.md)).

## Production build excludes the lab and notes
The lab lives outside `src/` and is never imported by the app. Each time the build is checked, `.output/` is searched for lab and model code (transformers, whisper, tesseract, `asr.worker`, `lab/`) and for the documentation files; none appear. The app has no route or link to the lab.

## Optional AI feedback for adults (off until connected)
- **Where:** the main practice’s “Have a listen back” screen only (`src/components/app/AiFeedback.tsx`, `useAiFeedback.ts`). The children’s corner never shows or uses it; a test checks this.
- **Switch:** off while `WORKER_URL` in `src/lib/ai-feedback/config.ts` is empty (the app then says “AI feedback isn’t connected yet” and the footer still says nothing is uploaded).
- **Consent:** turning AI feedback on is one page (`TurnOnPanel`) with one tick box for being 18 or over, reading in one’s own voice and agreeing to recordings going to AssemblyAI. The page says AssemblyAI may use recordings to train its models, that the free plan can’t switch this off, and that deleting a recording doesn’t undo training use. There’s no opt-out switch, because the backend can’t honour one. On or Off is remembered in `localStorage` (`src/lib/ai-feedback/choice.ts`, consent version 2) and changed from the card’s last row; turning it on always shows the page again. It is asked again if the training terms change.
- **What is sent:** nothing until the adult presses *Get notes on this recording*. Then only that recording’s audio goes to the Worker (`worker/`), which holds the AssemblyAI key as a secret and sends it to Universal-3.5 Pro on AssemblyAI’s EU servers. The passage and pages are never sent; the comparison, pauses and pace are worked out in the browser (`src/lib/reading-feedback/`).
- **Notes:** `buildFeedback` (`src/lib/reading-feedback/feedback.ts`) returns plain data: a pace sentence with words a minute every 20 seconds (silences measured from the audio taken out, only when the word timings pass the quality checks), and moments: pauses of 1.5 s or more inside a sentence with no words heard inside them, and skipped or repeated stretches of 3 or more words from lining up the transcript with the passage. Single-word differences aren’t reported. The notes are attached to the recording (`AudioTake.notes`) and saved with it in IndexedDB, so they are shown whenever that recording is, including after AI feedback is turned off.
- **Deletion:** the Worker deletes the transcript and uploaded audio from AssemblyAI as soon as the words are collected, and every 10 minutes sweeps any that were never collected. It stores no audio, words or passage text, only a daily total of audio seconds, each pending transcript’s counted seconds for a day, and a “credit ran out” flag (Workers KV). Request logging is off.
- **Limits and pauses:** 20 minutes per recording, 60 minutes a day in all. When AssemblyAI reports no credit, or the daily limit is reached, or the Worker is switched off, AI feedback pauses with a plain message; recording, playback and saving carry on. No card or top-up is on the AssemblyAI account, so running out never charges.
- **Provider:** behind a small interface (`worker/src/provider.ts`); only AssemblyAI is implemented and nothing switches automatically.
- Setup: [ai-feedback-setup.md](ai-feedback-setup.md). Evidence and its limits: [ai-feedback-experiment.md](ai-feedback-experiment.md).
